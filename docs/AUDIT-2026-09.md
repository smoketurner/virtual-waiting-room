# Design Audit — September 2026

Audit of [`DESIGN.md`](./DESIGN.md) against AWS service releases since late 2024. The
upstream solution was written against 2022-era primitives and deprecated in November
2025; several capabilities released in that window change this design materially.

**One finding is a correctness error in the design, not an optimization.** It is listed
first.

---

## 1. CRITICAL — the §4.3 throughput table is wrong

**The counter was never the binding constraint. `Positions` is.**

§4 spends its length proving that batch range allocation removes the single-partition
1,000 WCU/sec ceiling on `queue_counter`. That analysis is correct and it works. But each
batch performs **one** `UpdateItem` against `Counters` and **N** `PutItem`s against
`Positions` — one per visitor. Batching amortizes the counter write. It does nothing for
the position writes.

| Batch | §4.3 claimed ceiling | Counter WCU/s | `Positions` WCU/s | Reality |
|---|---|---|---|---|
| 10 | 10,000/s | 1,000 | 10,000 | within default quota |
| 100 | 100,000/s | 1,000 | 100,000 | **throttled at 40,000** |
| 1,000 | 1,000,000/s | 1,000 | 1,000,000 | **throttled at 40,000** |
| 5,000 | ~5,000,000/s | 1,000 | 5,000,000 | **throttled at 40,000** |

The default on-demand **per-table** quota is 40,000 WRU/s (adjustable via Service
Quotas). So the real ingest ceiling is ~40,000 joins/sec at default quotas, not 100,000
— the §4.3 default is overstated by 2.5×.

`Positions` is keyed on `request_id` (a UUIDv7), so it is evenly distributed and has no
hot-partition problem. This is purely a table-level throughput quota, and it is
raisable. But it must be *raised deliberately, in advance*, and the design did not say
so.

**Actions:**
- Correct the §4.3 table to show the `Positions` column as the governing limit.
- Add the DynamoDB per-table WRU quota increase to the pre-event readiness checklist
  alongside the API Gateway RPS increase.

## 2. CRITICAL — "zero cost at rest" collides with on-demand cold-start capacity

Design principle 3 is *zero cost at rest*, and §9 sells idle cost of ~$0. That principle
is in direct tension with how on-demand capacity scales:

> New on-demand tables will be able to sustain up to **4,000 writes per second** and
> 12,000 reads per second. On-demand capacity mode instantly accommodates **up to double
> the previous peak** traffic on a table.

A waiting room is idle 99% of the time. **An idle table has no meaningful previous
peak.** A freshly deployed waiting room throttles at ~4,000 writes/sec — 25× below the
design's stated 100,000/sec default — at exactly the moment a ticket on-sale begins.

This is the single most likely way a first production deployment fails, and nothing in
the current design prevents it.

### The fix: warm throughput / pre-warming (Nov 2024; GovCloud Jan 2025)

DynamoDB now exposes a **warm throughput** value and lets you **pre-warm** a table:

> Warm throughput value isn't a maximum limit on your table's capacity — rather, it's the
> minimum throughput that your table is prepared to handle instantaneously. If you
> pre-warm a table to support 100,000 write requests per second, your table will be ready
> to handle that traffic immediately.

This feature could not be more precisely aimed at this workload: a table that sits cold
and must absorb an instantaneous spike on a known schedule. Reading the warm throughput
value is free; pre-warming incurs a charge.

**Actions:**
- Expose `warm_throughput_write_units` / `read_units` as Terraform variables on
  `Positions` and `Counters`.
- Pre-warming becomes a **billable line item** in the pre-event readiness deliverable —
  it is a real cost incurred per event, on the client's behalf, with a concrete failure
  it prevents.
- Restate design principle 3 honestly: *near-zero cost at rest, with deliberate paid
  pre-warming before an event.* The current wording oversells it.

## 3. HIGH — Lambda Provisioned Mode for SQS ESM (Nov 2025) obsoletes a §8 bottleneck

§8 lists "SQS ESM poller ramp — +300/min → 1,250 max — **not adjustable**". That is now
false:

> SQS ESM configured with Provisioned Mode scales **3× faster** (up to 1,000 concurrent
> executions per minute) and supports **16× higher concurrency** (up to 20,000 concurrent
> executions) than default SQS ESM capability.

Configurable via min (2–200) and max (2–2000) event pollers; each poller handles up to
1 MB/s, 10 concurrent invokes, or 10 SQS polling API calls per second. Billed in Event
Poller Units (EPUs).

The ramp rate matters more than the ceiling here: a spike arriving in under five seconds
is exactly the case where +300 concurrent/minute is too slow, and 1,000/minute is
materially better.

**Caveat:** provisioned mode **cannot be combined with the maximum-concurrency setting**
— concurrency is controlled through poller count instead. That is a real Terraform module
design constraint, not a footnote.

**Actions:** make provisioned mode an opt-in variable, default off (it costs money at
rest, which conflicts with principle 3), enabled as part of pre-event readiness.

## 4. MEDIUM — WAF Anti-DDoS managed rule group (June 2025), with a caveat that matters

`AWSManagedRulesAntiDDoSRuleSet` detects, labels and challenges requests suspected of
participating in L7 DDoS, adds a **Challenge** action alongside Block/Count, and needs
**50 WCU** (down from the 150 Shield Advanced's previous protection required). AWS Shield
Advanced is adopting it as the default L7 protection.

**But it learns a traffic baseline, and this workload has a pathological baseline.** AWS's
own guidance:

> Give them time to establish their baselines before expecting them to respond
> appropriately to attacks. If you add these rules during an attack, after the attack
> subsides, the time to establish a baseline is usually from double to triple the normal
> required time.

A waiting room's "normal" is zero traffic, and its legitimate peak is indistinguishable
in shape from a volumetric attack. **Deploying this rule group in Block mode for a first
on-sale risks challenging or blocking legitimate visitors at the worst possible moment.**

**Actions:**
- Adopt it, but ship it in **Count mode by default**, with promotion to Block as an
  explicit per-client decision after observing at least one real event.
- Document the COUNT-then-BLOCK promotion discipline in the operator runbook.
- Also adopt **ASN matching** (June 2025) — useful against scalper infrastructure
  concentrated in known hosting ASNs, and cheaper than Bot Control for that specific case.

## 5. MEDIUM — CloudFront VPC origins (Nov 2024) improve the authorizer story

VPC origins let CloudFront serve from ALBs, NLBs, or EC2 instances in **private subnets**,
making CloudFront the sole ingress and removing the need for public IPs on the origin.

Two places this lands:

1. **The protected origin.** The waiting room's whole purpose is ensuring nobody reaches
   the origin without a token. VPC origins make that architecturally enforceable rather
   than merely policy-enforced — the origin is not on the internet at all. This
   strengthens the `modules/authorizer` story considerably.
2. **The GovCloud variant (§9).** That variant gates at ALB/origin because there is no
   edge compute. VPC origins are the natural fit — *if* they are available in the target
   region. **Must verify GovCloud availability**; the docs list supported regions
   explicitly and I have not confirmed GovCloud is among them.

## 6. Answered directly: CloudFront SaaS Manager / multi-tenant distributions

Released April 2025. Multi-tenant distributions with reusable config templates,
per-tenant parameters, ACM integration, and tiered pricing (~$0.10 per distribution
tenant/month beyond 200 tenants). WAF supports shared web ACLs across tenants with
optional per-tenant overrides and tenant identifiers in logs.

**Verdict: does not apply to our deployment model, and adopting it would undo §9.**

§9 deliberately rejects multi-tenancy because hosting other organizations' waiting rooms
in our account makes us a Cloud Service Provider requiring our own FedRAMP authorization
($250K–$2M, 6–24 months, ~$500K/yr). SaaS Manager is a tool for exactly the architecture
we decided not to build. It solves TLS/domain sprawl for a SaaS operator; we deploy into
the client's account, where each client has one domain and their own ACM.

**Where it is genuinely useful — a narrower case worth recording:** a *single* client
running many concurrent branded events (a ticketing company with dozens of venue domains,
a retailer with multiple brands). There, one client account holds many waiting-room
front-ends and SaaS Manager removes real per-domain toil. That is a Phase 5+ variant for
a specific customer profile, not a change to the core module.

Two constraints if that variant is ever built: multi-tenant distributions support **only
WAF V2 web ACLs**, and do not support Smooth Streaming (irrelevant here).

## 7. LOW — other releases evaluated

| Release | Relevance | Verdict |
|---|---|---|
| **DynamoDB configurable max throughput for on-demand** (May 2024) | Caps per-table WRU/RRU to bound cost | **Adopt as an optional variable.** A runaway or attack cannot then produce an unbounded DynamoDB bill. Note AWS applies it best-effort; burst capacity can exceed it. |
| **SQS fair queues** (July 2025) | Message group ID mitigates noisy-neighbor dwell time in shared queues | **Not for the single-event case.** Relevant only if one deployment serves multiple concurrent events on a shared queue — then `event_id` is the natural message group ID. Record as an option. |
| **CloudFront flat-rate pricing** (Nov 2025) | CloudFront dominates cost (§8a: ~17× the API Gateway bill) | **Investigate.** Not yet evaluated. Given that CloudFront request volume is the dominant cost line, a flat-rate plan could matter to the Phase 4 cost model. Flagged, not concluded. |
| **Bot Control v5.0** (March 2026) + expanded categories (Dec 2025) | Bot detection breadth | Adopt current version; no design change. |
